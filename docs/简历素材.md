## 一、项目概述

**栖选 AI 智能电商平台**｜Spring Boot 4 · MySQL 8 · Redis · Kafka · Vue 3 · MyBatis-Plus

面向买家与商家的双端电商系统，覆盖商品、购物车、下单、支付、发货、退款、秒杀全链路，并集成 LLM Agent 实现对话式操作（查订单、补货、发货），写操作走人在环审批。

- 买家端：浏览、购物车、结算、订单、秒杀、AI 助手
- 商家端：商品管理、分类、订单发货、退款审核、秒杀活动管理

## 二、AI Agent 层（差异化最强，优先写）

### 做了什么

LLM 不只是聊天，能**调用工具真正操作业务**：

```
用户："把无线鼠标的库存补到 500"
  → 模型选择工具 restockSku(skuId=1, qty=300)
  → 判定为写操作 → 不直接执行，生成审批单
  → 用户在页面点「通过」→ 事务内执行 → 写审计日志
```

### 三个值得讲的设计

**① 工具按角色下发，不是一股脑全给**

```java
// 所有登录用户：查询类工具
// 只有店铺 owner：补货、发货等写工具
public List<Map<String, Object>> definitions(Long userId)
```

**少给模型一个工具，它就少一条做错事的路。** 权限不该只写在提示词里，要写在工具清单里。

**② 写操作一律走"人在环"审批**

```
PENDING → APPROVED → EXECUTED
   ↓
REJECTED / EXPIRED（10 分钟未处理自动过期）
```

两个细节：

- **执行参数在创建审批单时就固化成 JSON**，审批通过后原样使用。否则用户看到的"补货 300 件"和实际执行的可能是两个数
- **10 分钟有效期**，避免"三天前的确认"被翻出来用

**③ 每次工具调用都留审计**

`ai_tool_audit` 记录：谁、在哪个会话、调了什么工具、入参、结果、耗时。

> 模型的行为不可完全预测，所以**它的每一步都要能回溯**。

### 后来补的四层护栏（面试很爱问）

```
① 轮次上限 5        —— 没有上限的循环 = 无限烧钱
② 连续失败熔断 2    —— 同一个坑不让模型试第三次
③ 时间预算 30s      —— 超时给部分结果，不让用户干等
④ 轮次间可中断      —— Redis 标志，每轮开始检查，命中就停
```

中断的粒度要说清楚：**只能在轮次之间停，单次 LLM 调用（最长约 20 秒）打断不了**。说清边界比夸大能力可信。

还有一个真实的坑：**工具失败后模型会自己编一句"已提交申请"**。
审计记录里工具明明返回 `{"error":"skuId 不存在"}`，模型却告诉用户成功。
代码层兜底：`consecutiveFailures > 0` 时不采用模型回答，直接返回"操作没有成功"。

> Agent 会为了让对话连贯而说谎 —— 不能信它的措辞，只能信工具返回值。

### 工具选择的工程化

读过一篇讲 tool selection 的文章后做的改造，四条都踩中了：

| 问题 | 修法 |
|---|---|
| `required` 误标 | 原来 `required = properties.keySet()`，把可选的 `limit` 也设成必填 → 模型填不上就**放弃调用整个工具**。改成显式指定 |
| 相似工具选错 | `get_order_status` / `list_my_orders` 等描述里互写"什么时候别用我、该用谁" |
| 工具缺 id 时反问用户 | 错误信息里直接给出 `availableSkuIds: [1]`，模型下一轮就能改对 |
| 会编造 id | 写操作返回 `displayText`，**该对用户的话由工具写好，模型只转发**，不让它自己组织数字 |

**Agent 选错工具，绝大多数不是模型笨，是工具工程（schema）的问题。**

### 流式输出（token 级 SSE）

```
LlmClient 逐行读 SSE → 文字增量回调 → SseEmitter 推 token 事件
                     → 工具调用按 index 分桶累加，流结束才解析参数
```

两个坑：① `arguments` 在流完前不是合法 JSON，中途 parse 必炸；② 多个 tool_call 的 delta 交错到达，必须用 `Map<index>` 分桶，不能用数组。

前端用 `fetch` + `ReadableStream`（EventSource 不支持 POST 和自定义头），SSE 事件按空行分隔，半截事件留在 buffer 等下一块。

用户侧效果：**文字逐字出现 + 工具执行时显示"正在查库存…" + 思考过程可折叠**。

### 简历措辞（替换原来那条）

> **AI Agent 集成**：基于 LLM Function Calling 实现对话式业务操作，8 个工具按角色动态下发；写操作转审批单二次确认（参数固化 + 10 分钟过期）+ 全量审计；实现 ReAct 多轮循环与四层护栏（轮次上限/失败熔断/时间预算/Redis 轮次中断）；工具调用改为 token 级 SSE 流式推送，工具参数按 index 分桶累加、流结束才解析；通过修正 required 误标、互斥式工具描述、参数纠错回传与 displayText 转发，解决模型放弃调用、选错工具与数字幻觉问题。

## 三、秒杀模块（性能，有硬数据）

### 做了什么

四轮压测定位瓶颈，QPS 从 240 提升到 3100。

### 归因链条（这段最能体现工程能力）

```
现象：L0 纯 DB 方案只有 240 QPS
假设 1：连接池太小        → 10→50，QPS 只涨 4%        → 否定
假设 2：客户端建连开销    → 改 keep-alive，+19%        → 部分成立
假设 3：客户端是天花板    → 打纯 Redis 接口得 4173     → 否定
假设 4：事务刷盘          → 数 fsync：500 单 817 次    → 命中
决定性证据：请求数翻倍（500→1000），总耗时几乎不变（2.21s→2.29s）
```

### 实测的基础组件能力

| 操作 | QPS | 说明 |
|---|---|---|
| Redis GET | 181,488 | 单命令、纯内存 |
| MySQL 主键查询 | 42,600 | buffer pool 全热 |
| MySQL 单条 INSERT | 2,000 | 每次 commit 刷盘 |

**读只差 4 倍，写差 90 倍**——Redis 快不是因为内存，是因为它敢不立即持久化。

### 最终方案

```
Redis Lua 预扣（挡流量 + 一人一单）
  → Kafka 排队（削峰）
  → 批量合并事务落库（500 单 3 个事务）
```

| 指标 | 优化前 | 优化后 |
|---|---|---|
| QPS | 240 | **3,100** |
| P95 | — | **22ms** |
| fsync 次数（500 单） | 2,000+ | **41** |

### 可靠性设计

| 机制 | 解决什么 |
|---|---|
| 唯一索引 `active` 列（NULL 不参与冲突） | 取消后无法再次抢购 |
| `INSERT IGNORE` + 唯一索引 | 至少一次投递下的重复消费 |
| 消费失败重试 3 次 → 死信队列 `seckill-order-dlt` | 毒消息不阻塞分区 |
| `BatchListenerFailedException` 标记批内位置 | 一条坏消息不拖累整批 |
| 定时对账（只往下修） | Redis 与 DB 漂移，宁少卖不超卖 |

### 故障注入验证

| 场景 | 结果 |
|---|---|
| Kafka 停机 | 3.2 秒返回 503 + 名额回补（默认配置会卡 60 秒打满线程池，已修复 `max.block.ms`） |
| Kafka 恢复 | 不重启应用，约 30 秒自动重新加入消费组，消息零丢失 |

### 简历措辞

> **秒杀模块**：通过分层压测定位瓶颈为 MySQL 事务 fsync（500 单产生 817 次刷盘），改用 Redis Lua 预扣 + Kafka 异步 + 批量合并事务，fsync 降至 41 次，QPS 240 → 3100、P95 22ms；配合唯一索引与死信队列保证零超卖、零丢单；故障注入验证 Kafka 宕机 3 秒快速失败、恢复后自动重连。

### 附加：商品列表的缓存收益实验（有对照组）

自己写了 aiohttp 异步压测脚本，做**缓存命中 vs 缓存击穿的对照实验**。
关键教训：第一次用 1 条商品测，命中/击穿几乎没差别（RPS 2745 vs 2866）——
**因为查询本身只要 0.5ms，缓存省的时间被固定开销淹没**。
造了 1 万条商品重测，差异才显现：

| 500 并发 / 1 万商品 | 缓存命中 | 缓存击穿 |
|---|---|---|
| RPS | 1612 | 238 |
| p99 延迟 | 741ms | 11393ms |
| 500 错误 | 0 | 29 个 |

击穿时 500 的原因是 Hikari 连接池（上限 50）获取连接超时——**连接池本身就是一道限流闸**，
DB 没被打死，但排队请求拖到了超时。

另一个数据点（1 条商品时的梯度压测）：

| 并发 | RPS | p99 |
|---|---|---|
| 200 | 1546 | 568ms |
| 1000 | 1888 | 1387ms |
| 5000 | **1537** ↓ | 8151ms |

**并发超过拐点后吞吐反降**——多出来的连接全在排队，没有产生价值。
结合 `Threads_connected=51 / Threads_running=2` 判定：瓶颈在应用连接池排队，不是数据库算力。

> 讲这段的价值：不是"我做了缓存"，而是"我知道缓存什么时候有效、什么时候没意义，
> 而且我用对照组数据证明了这一点"。这比背八股有说服力。

### 应用内令牌桶限流（漏斗入口的替代方案）

压测暴露了 5000 并发下系统被打爆，**补了一层应用内限流**（不是网关，定位要说清）：

```
拦截器识别具体 Controller 方法（HandlerMethod，不用字符串匹配路径）
  → Redis + Lua 令牌桶（补令牌 / 判断 / 扣减三步原子）
  → 商品列表 100 个/秒（桶容量 200），秒杀下单 20 个/秒（桶容量 40）
  → 拿不到令牌直接 429，不进业务方法
```

**429 前后对比（500 并发 / 5000 请求）**：

| | 无限流 | 令牌桶生效 |
|---|---|---|
| 200 / 429 | 5000 / 0 | 311 / **4689** |
| p99 延迟 | 8151ms（1 条数据时）| **376ms** |
| 应用状态 | 内存耗尽、JVM 起不来 | 平稳，无错误 |

放行数量 311 ≈ 桶容量 200 + 1.27 秒 × 100 个/秒 —— **令牌桶速率和实测吻合**，说明算法实现正确。

两个设计细节：
- **Redis 挂了要放行**：限流组件不能把整个应用拖垮，降级优先于精确
- **拦截器注册在鉴权之前**：被限掉的请求连认证都不用做

**边界（必须说清）**：这是"请求已进 Tomcat 之后"的限流，保护业务方法和 DB 连接池，
**保护不了 Tomcat 自己的线程池**。真正的网关限流（Nginx/Kong）挡在应用前面，本项目没做。

## 四、交易链路（体现业务建模能力）

### 库存三段式

```
available（可售）→ locked（下单锁定）→ sold（支付确认）
                        ↓
                   取消/关单 → 回到 available
```

三个状态对应三件事，**任何一步都靠条件更新保证不超卖**：

```sql
UPDATE sku_inventory
SET available_qty = available_qty - ?, locked_qty = locked_qty + ?
WHERE sku_id = ? AND available_qty >= ?
```

返回 0 行就是库存不足，**判断条件写进 WHERE，不写进 Java**。

### 订单状态机

```
PENDING_PAYMENT → PAID → SHIPPED → COMPLETED
       ↓            ↓
   CANCELLED    REFUNDING → REFUNDED
```

每个状态流转都用**条件更新**（`WHERE status = 旧状态`），影响行数不为 1 就抛 409。这样重复提交、并发状态变更都不会出错。

### 幂等设计

| 场景 | 手段 |
|---|---|
| 下单重复提交 | `client_request_id` 唯一索引 |
| 支付回调重复 | `payment_record` 唯一索引 |
| 秒杀转正式订单 | 业务号派生 + CAS 回填 |

### 简历措辞

> **交易链路**：设计 available/locked/sold 三段式库存模型，扣减用条件更新（`WHERE available >= ?`）保证不超卖；订单状态机每次流转校验前置状态；下单、支付回调、秒杀转单均通过业务号唯一索引实现幂等。

## 四·补、退款售后

### 三级状态判断

```
order_item（明细） → store_order（子单，按店铺拆分） → trade_order（主单）
```

"退完了吗"必须逐级向上判断：

1. 每条明细的**退款数量总和** ≥ 购买数量 → 该明细退完
2. 子单下所有明细都退完 → 子单 `REFUNDED`
3. 主单下所有子单都退完 → 主单 `REFUNDED`

**为什么不能"审核通过就把订单改成 REFUNDED"**：一单 3 件退 1 件，订单还是 `PAID`，只是那件标记已退。订单状态是"整体"的，退款是"局部"的操作。

### 两个真实踩过的 bug

| bug | 代码 | 后果 |
|---|---|---|
| `selectCount` 当 `sum` | `count += selectCount(...)` | 一次退 3 件只产生 1 条退款单，count=1 < 3，判定"没退完"，订单永远变不了 REFUNDED |
| 累加变量在循环外 | `int n = 0; for (item : items) { n += ... }` | 多条明细时，上一条的退款数污染下一条的判断 |

### 测试设计（比代码更值得讲）

**按 bug 的触发条件设计用例，不是按业务主流程：**

| 用例 | 能测出什么 |
|---|---|
| 买 1 件退 1 件 | 只能测主流程，count 和 sum 结果相同，**两个 bug 都测不出来** |
| 买 2 件分两次各退 1 件 | 测部分退不误判全退 |
| 买 3 件一次退 3 件 | **暴露 count vs sum 的语义错误** |

### 其他细节

- 审核用条件更新（`WHERE status = 'REQUESTED'`），影响行数 0 → 409，"重复审核"天然被挡住
- 更新状态用 `new Entity()` 只带 id 和 status，不整对象 `updateById`（避免把内存里的 null 写回库）
- 库存回滚走 `sold → available` 的条件更新，并写 `inventory_log` 流水

### 简历措辞

> 实现退款申请与商家审核流，按「明细 → 子单 → 主单」三级判断是否全部退完，全退时逐级同步状态并回滚库存（sold → available），审核通过条件更新防止重复处理。

## 五、权限体系

```
请求 → AuthInterceptor（token 有效？）→ 401
     → AdminInterceptor（是 ADMIN？）→ 403
     → Controller
```

三个细节：

- **401 和 403 语义分离**：未认证 vs 无权限。混用会导致"登录了但没权限 → 跳登录页 → 还是没权限"的死循环
- **角色从 DB 实时查，不放在 token 里**：权限宁可多查一次库，也不要拿过期信息
- **拦截顺序**：Auth 必须在 Admin 之前，否则拿不到 userId，所有人都 401

## 七、面试追问预案

| 会问 | 你要答 |
|---|---|
| "3100 怎么测的" | JMeter 1000 请求 / 200 并发 / 库存 500，跑 3 轮取稳定值 |
| "瓶颈在哪" | MySQL 事务 fsync，用 `Innodb_os_log_fsyncs` 验证 |
| "为什么不再优化" | 2884 已满足单商品秒杀场景，再优化要异步发送，丢"失败当场知道" |
| "Redis 挂了怎么办" | **目前没做降级，是已知缺口**（诚实回答，别编） |
| "超卖怎么防" | Redis Lua 原子扣减 + DB 条件更新双保险 + 对账兜底 |
| "重复消费怎么办" | `INSERT IGNORE` + 唯一索引，至少一次投递下的幂等 |
| "百万级大促怎么设计" | 我的项目实测到 3100 QPS，更大规模需要入口漏斗：CDN/Nginx 挡静态和恶意流量、网关令牌桶限流，Redis 之后的部分我已经有了。**网关层没实现，但我做了应用内令牌桶**：Redis+Lua 原子实现，压测 500 并发下 4689/5000 请求被 429 挡掉、p99 从 8 秒降到 376ms。边界：应用内限流保护不了 Tomcat 线程池，真网关要挡在应用前面 |
| "令牌桶为什么用 Lua" | 补令牌→判断→扣减是三步，拆成多条 Redis 命令有竞态，高并发下会一起通过。Lua 在 Redis 里串行执行才有原子性。和秒杀扣库存是同一个套路 |
| "缓存带来多大提升" | 用 1 万条商品做对照组：命中 RPS 1612 vs 击穿 238，p99 741ms vs 11.4s。**强调第一次用 1 条数据时看不出差异**——缓存的价值和数据量成正比，这个认知比数字本身重要 |
| "为什么 500 并发会报 500" | Hikari 连接池上限 50，慢查询时 500 个请求抢 50 个连接，等超时的就抛异常。连接池保护了 DB，但排队请求会超时 |
| "深分页怎么优化" | `LIMIT offset` 要扫过前面所有行；游标分页 `WHERE id < last_id` 走索引，代价是不能跳页 |
| "分组查询分页的坑" | MP 自动 count 生成 `COUNT(*) ... GROUP BY` 返回多行，取第一行当 total 就错了 → 手写不带 GROUP BY 的 count |
| "Agent 和 workflow 的区别" | 我们是 ReAct 循环，模型决定下一步调什么工具、何时收尾；workflow 是代码写死步骤。但**没做 Plan-and-Execute**，这是已知边界 |
| "测试覆盖率多少" | 别报总数（10%）。说清测了哪些边界、为什么测这些；覆盖率数字是减分项 |
| "为什么要 displayText" | 工具失败时模型会编"已提交成功"；让它转发工具写好的话，就不给自己组织数字的机会 |
