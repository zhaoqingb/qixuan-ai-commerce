## 核心结论（面试时先说这几句）

1. **零超卖不是"应该没问题"，是每轮压测都被证明过。**
   守恒式：`seckill_stock + sold_count` 恒等于初始库存；Redis 与 DB 两边账必须相等。

2. **优化要靠实验裁决，不能靠直觉。**
   四轮假设，前两轮被数据打脸，第三轮才命中真因。所有实验记录在 `04`。

3. **Redis 是闸门，不是账本。**
   DB 的 `seckill_stock` 才是最终真相，Redis 只负责把绝大多数请求挡在门口。

4. **缓存能让读变快，也能让"读到的旧值"变成线上事故。**
   凡是拿缓存值去做写操作的地方，都必须回源。

## 关键数字

| 指标 | 数值 |
|---|---|
| QPS 提升 | 240 → 3100（13 倍） |
| P95 延迟 | 977ms → 22ms |
| 每次压测的 fsync | 817 次 → 41 次 |
| 500 单的事务提交 | 500 个 → 3 个批次 |
| 单次 fsync 耗时 | 约 2.7ms（`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`） |

## 开发环境备注

- MySQL：`-h 127.0.0.1`（走 IPv6 的 localhost 会连不上）
- Redis：Docker 容器 `qixuan-redis`
- 压测脚本：临时目录下 `bench_keepalive.py`（连接复用版）、`bench_raw.py`（任意接口基线）
- 压测前必须：重置库存 → 清 Redis 的 `seckill:*` → 调 `/stock/sync` 预热 → **空跑一轮扔掉**
