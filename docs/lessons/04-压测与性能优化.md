# 04 · 压测与性能优化

> 完整链路：**240 → 460 → 2400 → 3100 QPS**，P95 从 977ms 降到 22ms。

## 一、最终数据

| 阶段 | QPS | 平均 | P95 | 每次压测的 fsync |
|---|---|---|---|---|
| L0 纯数据库 | ~240\* | — | — | — |
| L1 Redis 预扣 | 460 | 392ms | 977ms | **817** |
| L3 异步批量 | ~2400 | 17ms | 40ms | — |
| L3 + 本地缓存 | **~3100** | **11ms** | **22ms** | **41** |

\*L0 那轮用的老脚本，掺了客户端建连的水分，真实值更高

压测参数统一为 `--users 1000 --workers 200`，库存 500。

---

## 二、优化方法论（这一段比数字重要）

### 四轮假设，前两轮被数据打脸

```
假设 1：连接池太小
  实验：maximum-pool-size 10 → 50
  结果：QPS 351 → 366（+4%）
  裁决：错误，排除

假设 2：客户端建连开销
  实验：每请求 new HTTPConnection → 连接复用
  结果：366 → 437（+19%）
  裁决：对了一半，已经修掉

假设 3：客户端本身是天花板
  实验：用同样的客户端打 GET /stock（只做一次 Redis GET）
  结果：4173 QPS
  裁决：错误，客户端还有余量，问题在服务端

假设 4：事务刷盘
  实验：数 Innodb_os_log_fsyncs 增量
  结果：500 个订单 → 817 次 fsync，总耗时 2.21s，算出每次 2.7ms
  裁决：命中
```

**如果跳过实验直接调参**，最可能的结果是"把连接池调到 200，系统看起来正常了"，
然后永远不知道为什么 QPS 上不去。

### 决定性证据：请求数翻倍，总耗时不变

| 场景 | 请求数 | 成功数 | 总耗时 |
|---|---|---|---|
| 1000 用户抢 500 件 | 1000 | 500 | 2.29s |
| 500 用户抢 500 件 | 500 | 500 | 2.21s |

**请求数翻倍，总耗时几乎没变。**

说明总耗时不由请求数决定，而是由「成功订单数 × 每次事务的刷盘成本」决定。

---

### 前置：先测清楚每个组件的天花板

优化之前必须先知道"每个组件到底能跑多快"，否则无从判断瓶颈在哪。同一台机器、同一时段的实测：

| 操作 | 实测 QPS | 延迟 | 测试方式 |
|---|---|---|---|
| Redis GET | **181,488** | p50 0.143ms | `redis-benchmark -n 100000 -c 50 -t get` |
| MySQL 主键查询 | **42,600** | — | `mysqlslap --concurrency=50 --number-of-queries=20000` |
| MySQL 单条 INSERT | **2,000** | — | `mysqlslap --concurrency=50 --number-of-queries=3000` |
| 秒杀接口（完整链路） | **2,884** | P95 95ms | 1000 请求 / 200 并发 |

#### 这张表推翻了一个常见误解

"Redis 比 MySQL 快 10 倍"——**读和写的差距完全不是一个量级**：

```
Redis 读 vs MySQL 读    181,488 vs 42,600   →  只差 4 倍
Redis 写 vs MySQL 写    181,488 vs 2,000    →  差 90 倍
```

分水岭在**写**：MySQL 每次 commit 都要 fsync，Redis 默认 AOF `everysec` 不阻塞请求。

**Redis 快不是因为"内存比磁盘快"，而是因为"它敢不立即持久化"。**

#### 这张表解释了下文所有压测数据

| 现象 | 用这张表解释 |
|---|---|
| L0 纯 DB 只有 240 QPS | 一单约 4 次写（锁库存/订单/明细/流水），2000 ÷ 4 ≈ 500，叠加单行锁竞争降到 240 |
| L3 批量后到 3100 QPS | 500 单合成 3 个事务，fsync 从约 2000 次降到 41 次 |
| 现在 2884 不受 MySQL 2000 写入限制 | Kafka 把写操作移出用户路径，2000 的写能力被批量摊薄后够用 |

#### 结论

**不可能让"完整业务链路"达到"单条命令"的吞吐。** 能做只有三件事：

```
读慢 → 加缓存
写慢 → 排队（异步）
会丢 → 持久化 + 对账
```

秒杀架构的全部秘密就是这三条，没有第四条。

## 三、真正的原因：fsync

```sql
innodb_flush_log_at_trx_commit = 1     -- 每次提交 fsync redo log
sync_binlog                    = 1     -- 每次提交 fsync binlog
log_bin                        = ON
```

**每个事务提交要刷两次盘。**

```
500 个订单 = 500 个独立事务 = 817 次 fsync
817 × 2.7ms ≈ 2.2s    ← 和实测总耗时完全吻合
```

而且这些 fsync 是**串行**的——热点行的锁把 500 个事务排成了一队。

### 关键认知

**fsync 的成本是按"事务"付的，不是按"行"付的。**

一个事务里插 200 行，依然只刷两次盘。
所以解法不是"让 SQL 更快"，而是"减少事务个数"。

## 四、L3 异步下单的设计

### 结构

```
同步：请求 → Redis 预扣 → 事务[UPDATE + INSERT] → 返回
异步：请求 → Redis 预扣 → 丢进队列 → 立即返回 QUEUING
                              ↓
                   后台线程攒一批 → 事务[1次UPDATE + 1次批量INSERT]
```

### 代码骨架

```java
// 入队：必须非阻塞，满了返回 false（背压）
public boolean enqueue(SeckillOrder order) {
    return queue.offer(order);
}

// 消费：take() 睡等第一条，drainTo 把积压的全部捞走
private void loop() {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            List<SeckillOrder> batch = new ArrayList<>(BATCH_SIZE);
            batch.add(queue.take());
            queue.drainTo(batch, BATCH_SIZE - 1);
            flush(batch);
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt();
            return;
        }
    }
}
```

### 批量为什么能攒起来

```
时刻 0ms：队列空，线程在 take() 里睡着（不占 CPU）
时刻 1ms：请求 A 入队 → 线程被唤醒，take() 返回 A
时刻 1ms：B~Z 也陆续入队（不需要唤醒任何人）
时刻 1ms：线程从 take() 返回时，队列里已经躺着 49 个
          → drainTo 一把全捞 → 一次事务写 50 行
```

**不需要"等 50ms 攒一批"**，只要让线程在无事可做时真的睡着，
等待期间自然到达的订单就会聚成一批。

### 按 itemId 汇总

一批里可能混着多个商品，但 `deductStock(itemId, qty)` 一次只能扣一个商品：

```java
Map<Long, Integer> countByItem = new HashMap<>();
for (SeckillOrder order : batch) {
    countByItem.merge(order.getItemId(), 1, Integer::sum);
}
```

### 批量插入必须 `INSERT IGNORE`

```sql
INSERT IGNORE INTO seckill_order (...) VALUES (...), (...), (...)
```

`uk_seckill_user_item` 冲突时**跳过该行**而不是让整批失败。
Redis 的一人一单标记过期后，唯一索引是最后一道防线，它得"拒绝"不是"炸掉整批"。

### 代价（必须讲清楚）

1. **语义变化**：返回的"成功"是"名额已锁定"，不是"订单已创建"
2. **内存队列会丢**：进程崩溃，队列里没刷盘的订单就没了，但 Redis 名额已扣
3. **批量失败会静默吞单**：一批 200 条因库存漂移失败，这 200 个用户的"成功"是假的
4. **订单可见性延迟**：正常 20~50ms

生产环境必须换 MQ（RocketMQ/Kafka）靠消息持久化兜底。

## 五、最后的性能优化：本地缓存

`buy()` 里每次请求要查两次主键（item + activity），1000 并发 = 2000 次数据库往返，
**而且抢不到的人也要白查一遍**。

```java
private final ConcurrentHashMap<Long, Cached> cache = new ConcurrentHashMap<>();

public record Cached(SeckillItem item, SeckillActivity activity, long loadedAt) {}
```

- TTL 5 秒：活动状态变更最多延迟 5 秒生效
- 不做主动失效：秒杀期间商品信息几乎不变
- 并发下重复 `reload` 无害：查到的数据一样，最后写入的赢

**收益**：2400 → 3100 QPS，P95 40ms → 22ms。

详见 `03-Redis与缓存.md` 坑 7（缓存值不能用于写操作）。

## 六、压测本身的三个陷阱

### 陷阱 1：压测工具可能是瓶颈

```python
# ❌ 每请求新建连接
def call(path, token):
    conn = http.client.HTTPConnection(HOST, PORT)
    conn.request(...)
    conn.close()
```

1000 个请求 = 1000 次 TCP 握手。200 并发同时握手会打爆系统半开连接队列，
超出的 SYN 被丢弃，客户端 **1 秒后重传**。

**这就是 P95 稳定卡在 991ms 的来源**——测的是客户端建连能力，不是服务端。

修法：每个工作线程绑定一条长连接，读完 body 但**不 close**，后续请求复用。

验证：打印"新建 TCP 连接数"，应该是 `workers` 量级而不是请求数量级。

### 陷阱 2：冷启动数据不可信

同一份代码：
- 服务启动 42 秒时测：**1377 QPS**
- 热身后测：**2526 QPS**

差 83%。原因是 JVM 还在解释执行，热点代码没被 JIT 编译。

**固定流程：先空跑一轮扔掉，第二轮开始才计数。**

（和数据库 `innodb_buffer_pool` 预热是同一个道理，任何有状态的服务都有这个阶段。）

### 陷阱 3：用压测当第一个测试

单发冒烟必须单独做：抢一发、查 DB、查 Redis、验算守恒。
如果单个请求就有问题，1000 并发只会把错误放大 1000 倍，日志还会被淹掉。

## 七、压测前的固定流程

```bash
# 1. 重置数据
UPDATE seckill_item SET seckill_stock = 500, sold_count = 0 WHERE id = 1;
DELETE FROM seckill_order WHERE item_id = 1;

# 2. 清 Redis 残留（注意：前几轮的 seckill:user:* 会累积几百个 key）
docker exec qixuan-redis redis-cli EVAL \
  "local ks=redis.call('KEYS','seckill:*'); if #ks>0 then return redis.call('DEL',unpack(ks)) end; return 0" 0

# 3. 预热
curl -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/api/seckill/items/1/stock/sync

# 4. 空跑一轮（结果丢弃）

# 5. 正式两轮，取稳定值

# 6. 核对守恒
SELECT seckill_stock, sold_count FROM seckill_item WHERE id = 1;
SELECT COUNT(*), COUNT(DISTINCT user_id), SUM(amount) FROM seckill_order WHERE item_id = 1;
docker exec qixuan-redis redis-cli GET seckill:stock:1
```

**验收标准**：

- 成功笔数**正好等于**库存数（多一件就是超卖）
- `seckill_stock + sold_count` = 初始库存
- `COUNT(*) = COUNT(DISTINCT user_id)`（没有重复购买）
- `SUM(amount)` = 成功数 × 秒杀价
- Redis 库存 = DB 库存 = 0

## 八、还能往哪优化

| 方向 | 收益 | 代价 |
|---|---|---|
| 活动信息塞进 Redis Hash，Lua 里一并校验 | 省一次缓存查找（纳秒级） | 脚本变复杂，收益极小 |
| 换 `wrk` / `hey` 压测 | 看到真实上限 | 只是测量工具，不是优化 |
| 换真正的 MQ | 不丢单 | 要起 RocketMQ，改造消费者 |
| 多实例 + 网关分流 | 线性扩展 | 要解决 Redis 单点 |

**当前 3100 QPS 已经吃掉了 `GET /stock` 基线（4173）的 77%，
说明剩下的瓶颈在 HTTP 层和压测客户端，继续优化 Java 的边际收益很低。**

这个判断本身也是靠测量得出的——`GET /stock` 基线就是用来标定"客户端发射能力"的参照物。
