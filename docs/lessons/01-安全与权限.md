# 01 · 安全与权限

## 坑 1：越权访问（IDOR）—— 同一个错犯了 3 次

### 现象

```java
// 改购物车数量
CartItem item = cartItemMapper.selectById(cartItemId);   // ❌ 只按主键查
item.setQuantity(newQuantity);
cartItemMapper.updateById(item);
```

任何人拿到别人的 `cartItemId`，都能改别人的购物车。

### 原因

`selectById` 只保证"这一行存在"，不保证"这行属于你"。
主键是自增的，猜都能猜到。

### 修法

```java
CartItem item = cartItemMapper.selectOne(new LambdaQueryWrapper<CartItem>()
        .eq(CartItem::getId, cartItemId)
        .eq(CartItem::getUserId, userId));       // ✅ 归属条件进 WHERE
if (item == null) {
    throw new ResponseStatusException(HttpStatus.NOT_FOUND, "购物车项不存在");
}
```

### 关键点：为什么返回 404 而不是 403

| 返回 | 攻击者能推断出 |
|---|---|
| 403 Forbidden | "这个 id 存在，只是不属于我" → 可以枚举出系统里有多少条数据 |
| 404 Not Found | 什么都推断不出来 |

**信息隐藏原则**：对无权访问的资源，一律表现得像它不存在。

### 同类问题（一并修过）

- `ShipmentService.confirm()` 用了 `@RequestParam userId` → 改成 `@RequestAttribute("userId")`，
  从 token 解析，URL 里传的 userId 彻底失效
- 订单查询、退款查询都要带 `userId` 条件

### 面试怎么说

> 所有按 id 操作资源的接口，我都把 `userId` 写进查询条件，而不是查出来再比对。
> 因为查出来再比对有两个问题：一是多一次内存判断容易漏，二是返回值会泄露资源存在性。
> 查不到统一返回 404，攻击者无法区分"不存在"和"不属于你"。

## 坑 2：token 是无状态的，密钥泄露 = 全站身份伪造

### 设计

```java
// 格式：base64url(userId:expiresAt) + "." + base64url(HMAC-SHA256(body, secret))
public String issue(Long userId) {
    long expiresAt = Instant.now().getEpochSecond() + ttlSeconds;
    String payload = userId + ":" + expiresAt;
    String body = ENCODER.encodeToString(payload.getBytes(UTF_8));
    return body + "." + ENCODER.encodeToString(sign(body));
}
```

原理和 JWT 一样：服务端不存 token，只验签名。

### 安全要点

1. **签名比较必须用 `MessageDigest.isEqual`**，不能用 `equals`
   逐字节比较会在第一个不同的字节就返回，攻击者可以通过响应时间差猜出签名。

2. **密钥不能进版本控制**
   `app.auth.secret` 写在 `application.properties` 里，这个文件已在 `.gitignore`；
   仓库里只提交 `application.properties.example`，密码占位 `CHANGE_ME`。

3. **要清楚代价**
   secret 泄露 → 任何人可以给自己签发任意 userId 的 token。
   我们在压测时正是利用这一点批量伪造了 1000 个用户。

### 面试怎么说

> 用 HMAC 签名的无状态 token，服务端不存会话，验签即可。
> 两个细节：签名比较用 `MessageDigest.isEqual` 防时序攻击；密钥走环境变量注入，不进仓库。
> 代价我清楚——密钥泄露等于全站身份可伪造，所以密钥必须是长随机串并且能轮换。

## 坑 3：`@RequestParam userId` 是自欺欺人

### 现象

```java
// ❌ 前端传什么就是什么
public Result add(@RequestParam Long userId, @RequestBody CartAddRequest req)
```

URL 里改个数字就能操作别人的数据，token 校验形同虚设。

### 修法

拦截器验完 token 后：

```java
request.setAttribute("userId", tokenService.verify(token));
```

Controller 里：

```java
public Result add(@RequestAttribute("userId") Long userId, @RequestBody CartAddRequest req)
```

**身份只能来自凭证，不能来自请求参数。** 这条是硬规矩。

## 坑 4：BCrypt 校验用错了方法

```java
// ❌ 又把密码哈希了一遍，永远不相等
if (passwordEncoder.encode(rawPassword).equals(user.getPasswordHash()))

// ✅ matches 会从存储的哈希串里解析出盐，再用同样的盐算一遍
if (passwordEncoder.matches(rawPassword, user.getPasswordHash()))
```

### 原理

BCrypt 的哈希串自带盐，格式是 `$2a$10$<22位盐><31位哈希>`。
`encode` 每次都生成**新的随机盐**，所以两次 encode 同一个密码结果不同。
`matches` 做的事是：从旧串里取出盐 → 用这个盐算一遍 → 比对。

## 坑 5：秒杀接口没有做权限收敛

`/api/seckill/items/{id}/stock/sync`（预热库存）、`/api/db-check` 这类运维接口，
当前是在鉴权范围内但**没有角色校验**——任何登录用户都能调。

正式部署前必须：
- 收进管理员权限，或
- 直接下线

已在代码注释里标注为待处理项。
