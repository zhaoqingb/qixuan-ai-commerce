# 07 · 秒杀模块设计

> 从 240 QPS 到 3100 QPS，从"抢到就没下文"到完整闭环。这一篇记的是**决策和取舍**，
> 具体的坑在 01~04 里。

## 一、整体链路

```
① 活动配置   reserve 预留库存        available → locked，库存不够在这里就报错
② 抢购       Redis Lua 预扣 → 队列 → 批量落库 seckill_order      3100 QPS
③ 查看       秒杀页「我的秒杀记录」  /api/seckill/orders
④ 转正单     trade_order + store_order + order_item，CAS 回填   幂等
⑤ 支付       locked → sold（走现有 PaymentService）
⑥ 发货       走现有 ShipmentService
⑦ 取消       回补 Redis + seckill_item，名额还给池子
⑧ 对账       每 30 秒用 DB 校正 Redis，只往下修不往上修
```

## 二、三个关键设计决策

### 决策 1：Redis 是闸门，不是账本

| 存哪 | 作用 | 能不能丢 |
|---|---|---|
| Redis `seckill:stock:{id}` | 挡掉绝大多数请求 | 能丢，对账会修 |
| Redis `seckill:user:{id}:{uid}` | 一人一单的快速判断 | 能丢，唯一索引兜底 |
| `seckill_item.seckill_stock` | 最终账本 | 不能丢 |
| `seckill_order` | 抢到凭证 | 不能丢 |

**Redis 挂了最多让流量回落到数据库，绝不能让抢购直接 500。**

### 决策 2：抢购快、创单慢 —— 不把低频操作塞进高频路径

最初想"抢到即创单"，但 `order_item.store_order_id` 依赖 `store_order` 的自增主键，
而**批量 INSERT 拿不到每行的 id**。于是整条链路会从"一次批量插入"退化成
"每单逐条插三张表"：

```
现在：     500 单 → 3 个批量事务 → 41 次 fsync → 3100 QPS
抢到即创单：500 单 → 1500 条逐条插 → 500+ 次 fsync → 掉回 500 以内
```

所以拆成两段：抢购只写 `seckill_order`（高频，批量），
用户点「去支付」时才建正式订单（低频，逐条无所谓）。

**判据：拿 90% 的性能去换 10% 的体验提升，是亏的。**

### 决策 3：库存不够，要在"配置阶段"失败，不能在"付款阶段"

秒杀池（`seckill_item.seckill_stock`）和 sku 可用库存（`sku_inventory.available_qty`）
原本是两本互不相干的账。活动配了 500 件、sku 只有 138 件可用时：

| 校验位置 | 谁发现 | 什么时候 | 代价 |
|---|---|---|---|
| 用户付款时 | 用户 | 抢到之后 | 体验灾难，用户白抢 |
| 活动配置时 | 运营 | 上线之前 | 改个数字而已 |

所以加了 `reserve` 接口：**活动上线前把这批货从 `available` 划到 `locked`**。

```
reserve:  available -= N, locked += N, 记录 reserved_qty
转单:     reserved_qty > 0 时【不再锁库存】，否则兜底现锁一件
支付:     locked → sold
释放:     活动结束，把没卖出去的（= 当前 seckill_stock）从 locked 还回 available
```

**同一个校验，放在不同位置，代价差几个数量级。**

## 三、为什么转单时不能重复锁库存

预留过的活动，那批货已经整体锁在 `locked` 里了。转单时再 `lockStock` 一次，
等于同一件货扣两次，`locked` 虚高，最后支付时账就对不上：

```java
int reservedQty = sku.reservedQty() == null ? 0 : sku.reservedQty();
if (reservedQty == 0) {
    if (skuInventoryMapper.lockStock(sku.skuId(), 1) == 0) {
        throw new ResponseStatusException(CONFLICT, "商品库存不足，暂时无法生成订单");
    }
}
```

## 四、并发控制清单（这个模块用到的全部武器）

| 场景 | 武器 | 为什么 |
|---|---|---|
| 库存扣减 | 条件 UPDATE（CAS） | 判断进 WHERE，返回值当判据 |
| 一人一单 | Redis `EXISTS` + 唯一索引 | 快路径 + 数据库兜底 |
| 取消后重买 | `active` 列参与唯一索引 | NULL 不参与冲突（见 02 坑 8） |
| 转单幂等 | `client_request_id` 派生自秒杀单号 | 同单永远只出一张正式单 |
| 并发转单 | `WHERE trade_order_id IS NULL` | 只有一个人能把 NULL 改成功 |
| 重复预留 | `WHERE reserved_qty = 0` | 同上 |
| 预扣原子性 | Lua 脚本 | 单线程执行期间不插入其他命令 |
| Redis 漂移 | 定时对账，只往下修 | 宁少卖不超卖 |

## 五、完整验收标准

每轮压测后逐条核对：

```
1. 成功笔数 == 库存数                     （多一件就是超卖）
2. seckill_stock + sold_count == 初始库存  （守恒式）
3. COUNT(*) == COUNT(DISTINCT user_id)    （没有重复购买）
4. SUM(amount) == 成功数 × 秒杀价
5. Redis 库存 == DB 库存
6. sku: available + locked + sold == 总量  （预留和支付都不改变总数）
7. inventory_log 流水与状态变化一一对应
```

## 六、已知缺口（还没做）

| 缺口 | 影响 |
|---|---|
| 秒杀订单取消后，`sku_inventory` 的 locked 不回收 | 那件货回到秒杀池了，但 sku 的 locked 还占着；活动结束 release 时按 `seckill_stock` 算，账能对上，但中间态不精确 |
| 已转单未支付的订单超时关闭 | `OrderCloseJob` 会把 locked 还给 available，而不是还回秒杀池 → 走这条路会造成漂移 |
| 活动管理页面 | reserve / release 只有接口，没有 UI |
| 秒杀记录接口直接返回实体 | `active`、`userId` 等内部字段暴露，应改成 `SeckillOrderView` |
| 内存队列 | 进程崩溃丢单，生产要换 MQ |

## 七、面试怎么讲这个模块

> 秒杀我做了四轮优化，从 240 QPS 到 3100。
>
> 关键是**没有靠猜**：第一轮我以为连接池太小，调到 50 只涨 4%，被数据打脸；
> 第二轮发现压测脚本每请求新建 TCP 连接，P95 卡在 991ms 正好是 SYN 重传超时；
> 第三轮打了一个只做 Redis GET 的基线接口，测出客户端能到 4000，确认问题在服务端；
> 第四轮数 `Innodb_os_log_fsyncs`，500 个订单产生 817 次 fsync × 2.7ms = 2.2s，
> 和总耗时完全吻合——真因是每个订单一个事务、每个事务刷两次盘。
>
> 解法是异步批量：Redis 预扣成功后丢队列立即返回，后台线程用 `take() + drainTo`
> 攒批，一次事务写 200 行。fsync 从 817 降到 41，QPS 到 2400，再加本地缓存到 3100。
>
> 但我没有做"抢到即创单"，因为 `order_item` 依赖子单自增 id，批量插入拿不到，
> 会退化成逐条插入，把优化全部吃掉。所以拆成"抢购快、创单慢"。
>
> 最值得说的一课是**失败位置**：库存不够原本在用户付款时才报错，
> 我把它前移到活动配置阶段的库存预留，让运营而不是用户承担后果。
