# 02 · 并发与事务

## 坑 1：丢失更新 —— `updateById` 改库存会超卖

### 错误写法

```java
SeckillItem item = itemMapper.selectById(itemId);
item.setSeckillStock(item.getSeckillStock() - 1);
itemMapper.updateById(item);
```

### 为什么会超卖

库存剩 1 件，两个请求同时进来：

```
A: selectById → stock = 1 → setStock(0)
B: selectById → stock = 1 → setStock(0)
A: UPDATE seckill_item SET seckill_stock = 0 WHERE id = 1   ✅
B: UPDATE seckill_item SET seckill_stock = 0 WHERE id = 1   ✅
```

两单都成功，库存只减了 1。

生成的 SQL 是 `SET seckill_stock = 0`——**一个由 Java 算好的常量**，
数据库完全不知道"应该基于当前值减一"。

### 正确写法

```sql
UPDATE seckill_item
SET seckill_stock = seckill_stock - #{qty},
    sold_count    = sold_count + #{qty}
WHERE id = #{itemId}
  AND seckill_stock >= #{qty}
```

```java
int rows = itemMapper.deductStock(itemId, 1);
if (rows != 1) {   // 0 就是没抢到，不要用 == 0 判断后再补 else，影响行数只可能是 0 或 1
    throw new ResponseStatusException(HttpStatus.CONFLICT, "手慢了，已售罄");
}
```

### 为什么这样就不超卖

1. `SET stock = stock - 1` 是**数据库层面的读-改-写**，不需要 Java 先读
2. `WHERE stock >= 1` 的判断在**同一把行锁**内完成
3. InnoDB 拿到锁后会做**当前读**（不是快照读），看到的是最新值

第二个请求进来时库存已经是 0，`rows` 返回 0。

### 判据（记住这条）

> **秒杀的库存扣减，绝不能先读出来、在 Java 里算、再写回去。判断条件必须进 WHERE。**

### 什么时候 `updateById` 是安全的

实体上如果有 `@Version` 乐观锁，`updateById` 会带上版本号条件，冲突时返回 0 行。
但 `SeckillItem` 没有 `version` 字段，这里的 `updateById` 是**裸的覆盖写**。

## 坑 2：写偏斜（write skew）—— 退款超量

### 现象

退款申请接口，逻辑是"先查已退金额，判断不超总额，再插入记录"：

```java
BigDecimal refunded = sumRefunded(orderNo);           // ① 读
if (refunded + request.amount() > paidAmount) {       // ② 判断
    throw new BizException("超额");
}
refundMapper.insert(...);                             // ③ 写
```

20 个并发抢 3 个退款名额，**成功了 11 个**。

### 为什么 CAS 救不了

它冲突的不是同一行，而是"读到的那个集合"。每笔插入的都是新行，
行锁根本不冲突，只有 `SELECT` 时加锁才能拦住。

### 修法：悲观锁

```java
// 把订单行锁住，后面的请求排队
Order order = orderMapper.selectOne(new LambdaQueryWrapper<Order>()
        .eq(Order::getOrderNo, orderNo)
        .last("FOR UPDATE"));
```

实测：20 并发 → 3 成功。

### `FOR UPDATE` 与乐观锁的关系

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 假设 | 一定会冲突，先锁住 | 大概率不冲突，提交时检查 |
| 实现 | `SELECT ... FOR UPDATE` | `UPDATE ... WHERE version = ?` |
| 失败处理 | 等待（阻塞） | 返回 0 行，业务层重试 |
| 适用 | 冲突频繁、逻辑复杂（需要读多行再算） | 冲突少、单行更新 |

**选择判据**：能不能把判断塞进 `WHERE`？
能 → 一条条件 UPDATE（CAS）。不能（要先读集合再算）→ 悲观锁。

## 坑 3：`@Transactional` 自调用不生效

### 现象

```java
public void outer() {
    this.inner();      // 事务注解不生效！
}

@Transactional(propagation = REQUIRES_NEW)
public void inner() { ... }
```

Spring 的事务靠 AOP 代理实现。`this.inner()` 调用的是**原始对象**，
根本没经过代理，所以注解被忽略。

### 实际踩到的场景

`AiApprovalExpiryService.markExpired()` 把审批标记为过期后抛异常，
期望"过期标记保留、主流程失败"。结果标记也跟着回滚了。

### 修法：`REQUIRES_NEW` 必须跨 Bean

把 `markExpired` 放到另一个 `@Service` 里，通过注入调用，代理才生效。

## 坑 4：事务里不能有远程调用

### 错误写法

```java
@Transactional
public SeckillResult buy(Long userId, Long itemId) {
    itemMapper.selectById(itemId);        // 事务已开始，占着连接
    stockService.tryDeduct(...);          // Redis 调用，可能卡 2 秒
    itemMapper.deductStock(...);
    orderMapper.insert(...);
}
```

### 后果

Redis 抖动 1.8 秒（还没到 2 秒超时），这 1.8 秒里事务一直开着，
**占着一个数据库连接什么都不干**。并发上来连接池直接被"空转事务"占满。

### 修法：收窄到只包 DB 操作

```java
public SeckillResult buy(Long userId, Long itemId) {
    // 无事务：查商品、校验活动、Redis 预扣
    ...

    try {
        return transactionTemplate.execute(status -> {
            // 有事务：只有这两行
            int rows = itemMapper.deductStock(itemId, 1);
            if (rows != 1) throw new ResponseStatusException(CONFLICT, "已售罄");
            orderMapper.insert(order);
            return new SeckillResult(...);
        });
    } catch (RuntimeException ex) {
        stockService.rollback(itemId, userId);   // 补偿 Redis
        throw ex;
    }
}
```

**为什么用 `TransactionTemplate` 而不是 `@Transactional`**：
自调用问题不存在，事务边界一目了然，也不需要新建一个类。

### 实测数据

收窄事务后 QPS 437 → 460（+5%），**提升很小**。
因为它解决的是正确性问题，不是吞吐问题——吞吐卡在 fsync 上（见 `04`）。

## 坑 5：一个 catch 兜住整段，比每个失败点手动补偿可靠

```java
try {
    int rows = itemMapper.deductStock(itemId, 1);
    if (rows != 1) throw new ResponseStatusException(CONFLICT, "已售罄");
    orderMapper.insert(order);
    return ...;
} catch (DuplicateKeyException ex) {
    stockService.rollback(itemId, userId);
    throw new ResponseStatusException(CONFLICT, "每人限购1件");
} catch (RuntimeException ex) {
    stockService.rollback(itemId, userId);
    throw ex;
}
```

**一个失败点写一次补偿必然会漏**。包一层 catch，任何路径抛异常都会走到补偿。

注意 catch 顺序：`DuplicateKeyException` 是 `RuntimeException` 的子类，
**子类必须写在前面**，否则永远捕获不到。

## 坑 6：单号生成的生日悖论

### 现象

`时间戳(秒) + 4 位随机数`，500 单**撞了 9 次**。

### 计算

每秒 9000 个格子（0000-9999），放 n 个样本，期望碰撞数：

```
n² / (2 × 9000) = 500² / 18000 ≈ 14
```

实测 9 次，量级吻合。

### 修法：雪花 ID

```java
private String generateOrderNo() {
    return "SK" + IdWorker.getIdStr();
}
```

`workerId + 毫秒时间戳 + 序列号`，同毫秒内靠序列号区分，单机唯一性有保证。

### 面试怎么说

> 单号我一开始用时间戳加随机数，压测 500 单撞了 9 次。
> 算一下就是生日悖论：n 个样本落在 M 个格子里，期望碰撞约 n²/(2M)。
> 后来换成雪花 ID，workerId + 毫秒 + 序列号，同毫秒靠序列递增保证唯一。

## 坑 8：唯一索引不认状态 —— 取消后无法再次购买

### 现象

用户抢到秒杀商品 → 取消订单 → 再抢一次，接口返回"抢购成功"，
但**订单表里查不到这一单**，而库存已经被扣了。

```
DB      seckill_stock 499, sold_count 1
订单表   只有 1 行：CANCELLED
```

### 根因

```sql
UNIQUE KEY `uk_seckill_user_item` (`user_id`, `item_id`)
```

这条索引只看这两列，**完全不管 status**：

```
第一次抢 → 插入 (9001, 1) ✅
取消     → 只把 status 改成 CANCELLED，行还在
第二次抢 → INSERT IGNORE (9001, 1) → 撞唯一索引 → 静默跳过
```

`INSERT IGNORE` 的本意是"兜住重复下单"，结果把"取消后重新购买"这个**合法场景**也一起吞了。

### 为什么比报错更可怕

它是**静默**的。接口返回成功、库存扣了、Redis 也扣了，
只有订单没落库 —— 用户的名额蒸发，日志里一条错误都没有。

如果是抛异常，压测或冒烟立刻就能发现。

### 解法：让唯一索引只约束"有效订单"

```sql
ALTER TABLE seckill_order ADD COLUMN active TINYINT NULL DEFAULT 1;

-- 历史数据必须先修正，否则老用户仍然买不了
UPDATE seckill_order SET active = NULL WHERE status = 'CANCELLED';

DROP INDEX uk_seckill_user_item ON seckill_order;
CREATE UNIQUE INDEX uk_seckill_user_item ON seckill_order (user_id, item_id, active);
```

利用 MySQL 的规则：**唯一索引里多个 NULL 不算重复**。

| 场景 | 索引值 | 是否冲突 |
|---|---|---|
| 两条有效订单 | `(9001,1,1)` vs `(9001,1,1)` | 冲突，防一人多单 |
| 有效 + 已取消 | `(9001,1,1)` vs `(9001,1,NULL)` | 不冲突，可以再买 |
| 两条已取消 | `(9001,1,NULL)` vs `(9001,1,NULL)` | 不冲突 |

### 为什么不用 `cancelled_at` 时间戳

同样的思路会想到 `cancelled_at`（未取消为 NULL，取消时写时间）。
**但方向是反的**：

```
未取消：cancelled_at = NULL  → (9001,1,NULL)
已取消：cancelled_at = 时间   → (9001,1,'2026-...')
```

这样**未取消**的记录带 NULL，多行 NULL 不冲突 —— 唯一索引完全失效，一人可以下无数单。

所以：**参与唯一索引的那一列，必须是"有效时有值、无效时为 NULL"**，不能反过来。

### 踩到的第二个坑：MyBatis-Plus 的 null 语义

```java
// ❌ active 根本不会被更新
SeckillOrder patch = new SeckillOrder();
patch.setActive(null);
orderMapper.update(patch, wrapper);
```

实体更新默认策略是 `FieldStrategy.NOT_NULL`——null 意味着"这个字段不改"。
我们恰恰要"把它改成 null"，必须用 wrapper：

```java
// ✅
orderMapper.update(null, new LambdaUpdateWrapper<SeckillOrder>()
        .set(SeckillOrder::getStatus, ORDER_CANCELLED)
        .set(SeckillOrder::getActive, null)
        .eq(SeckillOrder::getId, order.getId())
        .eq(SeckillOrder::getStatus, ORDER_SUCCESS));
```

**同一个 API 里，"传实体"和"用 wrapper.set"的 null 语义是相反的。**

### 验收

```
抢 → CANCELLED(active=NULL) → 再抢 → SUCCESS(active=1)   ✅ 两行都在
同一用户第三次抢 → 409 每人限购1件                        ✅ 防重复仍生效
库存 499 + sold_count 1 = 500                            ✅ 守恒
```

### 面试怎么说

> 秒杀加了"取消订单"之后发现一个静默 bug：唯一索引 `(user_id, item_id)` 不看状态，
> 取消后行还在，用户再买时 `INSERT IGNORE` 会撞索引被跳过——库存扣了、订单没落库。
>
> 因为是 `INSERT IGNORE`，整个过程不报错，只能靠对账发现。
> 解法是加一个 `active` 列参与索引：有效时 1，取消时 NULL，
> 利用 MySQL「唯一索引里多个 NULL 不算重复」的特性，让它只约束有效订单。

## 坑 9：影响行数当并发信号

```java
if (rows != 1) {
    throw new ResponseStatusException(HttpStatus.CONFLICT, "状态已变化，请刷新重试");
}
```

- `rows == 1`：精确更新了一行，成功
- `rows == 0`：条件不满足（库存没了 / 状态已变 / 不属于你）
- `rows > 1`：说明 WHERE 写漏了，是 bug，不能当成功

**不要写 `if (rows == 0) {...} else if (rows == 1) {...} else {...}`**，
`!= 1` 一句话覆盖所有异常情况，语义更硬。

状态机改造（发货）用的就是这套：

```sql
UPDATE store_order SET status = 'SHIPPED'
WHERE id = ? AND status = 'PAID'
```
