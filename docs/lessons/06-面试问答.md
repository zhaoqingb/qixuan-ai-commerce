# 06 · 面试问答速查

> 每条都是"问题 → 30 秒能讲完的骨架"。细节去对应文件里翻。

## Q1：秒杀怎么防超卖？

**四层防线，从外到内：**

1. **Redis Lua 原子预扣**：判断库存和扣减在同一个脚本里，Redis 单线程执行期间不插入其他命令
2. **DB 条件更新**：`UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock >= 1`，判断进 WHERE
3. **唯一索引兜底**：`uk_seckill_user_item(user_id, item_id)` 防一人多单
4. **对账**：定时用 DB 校正 Redis，只往下修不往上修

**关键点**：Redis 是闸门不是账本，DB 才是最终真相。

---

## Q2：为什么用 Lua，不用 Redis 事务？

`MULTI/EXEC` 只是把命令打包按顺序执行，**中间不能读结果做判断**
（WATCH 能做乐观锁，但要重试）。

Lua 可以在脚本里 `if` 判断后再 `DECR`，这是监控库存场景刚需。

而且 Lua 执行期间 Redis 不会被其他命令打断——这是原子性的来源。

**但要注意**：Lua 不是数据库事务，**没有回滚**。已执行的写不会因为 `return` 撤销。

---

## Q3：异步下单后，用户拿到的"成功"是真的吗？

**是"名额锁定"，不是"订单已创建"。**

这是架构的固有代价。接口返回 `QUEUING` + 订单号，前端轮询状态接口确认。

生产上还要配：
- MQ 保证消息不丢（内存队列进程崩溃就丢）
- 对账兜底（批量失败时这 200 个用户的"成功"是假的）
- 超时补偿（长时间 `QUEUING` 要主动置为失败并释放名额）

## Q4：QPS 怎么从 240 提到 3100 的？

```
L0 纯数据库          240
  ↓ Redis 预扣        460    挡住一半请求不碰 MySQL
  ↓ 异步批量 + 收窄事务 2400   fsync 817 → 41
  ↓ 本地缓存         3100    干掉两次主键查询
```

**但真正想讲的不是数字，是过程**：四轮假设，前两轮被数据打脸。

- 连接池 10→50，只涨 4% → 排除
- 客户端改连接复用，涨 19% → 对了一半
- 打 `GET /stock` 基线得 4173 → 客户端不是天花板
- 数 fsync：817 次 × 2.7ms = 2.2s，和总耗时吻合 → 命中

## Q5：怎么发现是 fsync 的？

**两个证据叠起来：**

1. `SHOW STATUS LIKE 'Innodb_os_log_fsyncs'` 压测前后对比，500 个订单产生 **817 次** fsync
2. 一个反常现象：**请求数翻倍（500→1000），总耗时几乎不变（2.21s → 2.29s）**

第二条说明总耗时不由请求数决定，而是由"成功订单数 × 每次事务刷盘成本"决定。

配置是 `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`，每个事务刷两次盘。

## Q6：为什么收窄事务只涨了 5%？

因为它解决的**不是吞吐问题，是正确性问题**。

吞吐卡在 fsync 上——每个事务提交刷两次盘，这是物理开销，事务圈多大都一样。

收窄事务的价值在于：**事务里不能有远程调用**。
Redis 抖动 1.8 秒，事务就持锁 1.8 秒，占着连接什么都不干。

5% 这个数字反而验证了判断：如果收窄事务涨了很多，说明原来真的卡在锁竞争上。

## Q7：对账为什么"只往下修不往上修"？

```
DB = 500，Redis = 400  → 看起来不一致，但其实是队列里 100 单还没落库
```

如果按 DB 把 Redis 重置成 500：

```
又卖 500 个 + 队列里 100 单落库 = 卖了 600 → 超卖
```

所以规则是单向的：

| 情况 | 动作 |
|---|---|
| Redis > DB | 危险（超卖风险）→ 修正成 DB 的值 |
| Redis < DB | 正常中间状态 → 不动 |
| Redis = null | key 丢了 → 用 DB 重建 |

**总结成一句：宁少卖，不超卖。**

## Q8：怎么保证压测结论可信？

**三个坑都踩过：**

1. **压测工具本身是瓶颈**：每请求新建 TCP 连接，200 并发握手打爆半开队列，
   SYN 重传超时正好 1 秒 → P95 卡在 991ms。改成连接复用。
2. **冷启动不可信**：同一份代码，启动 42 秒时测 1377，热身后 2526，差 83%。
   固定流程：空跑一轮扔掉。
3. **压测不能当第一个测试**：先单发冒烟，验库存、验订单、验守恒。

**验收标准**：成功数正好等于库存数；`stock + sold_count` 等于初始值；
订单数和买家数相等；金额合计对得上。

## Q9：`@Transactional` 有哪些坑？

1. **自调用不生效**：`this.inner()` 绕过 AOP 代理。`REQUIRES_NEW` 必须跨 Bean。
2. **事务里做远程调用**：Redis 卡 1.8 秒，事务持锁 1.8 秒。
3. **异常被吞掉不回滚**：catch 住不抛，Spring 认为成功。要么重新抛，要么 `setRollbackOnly()`。
4. **默认只回滚 RuntimeException**：受检异常要显式 `rollbackFor`。
5. **事务范围过大**：方法一进来就 `getConnection()`，Redis 操作期间也占着连接。

## Q10：怎么防越权（IDOR）？

**把 `userId` 写进查询条件，而不是查出来再比对。**

```java
selectOne(id + userId)          // ✅
selectById(id) 然后比对 userId   // ❌
```

**查不到统一返回 404 而不是 403**：
403 等于告诉攻击者"资源存在，只是不属于你"，本身就是信息泄露。

身份只能来自凭证（token → `@RequestAttribute`），不能来自请求参数（`@RequestParam userId`）。

---

## Q11：缓存有哪些坑？

1. **缓存值不能用于写操作**：5 秒陈旧的库存值灌进 Redis = 凭空放名额 = 超卖。
   **读可以用缓存，写必须回源。**
2. **预热用 `setIfAbsent` 不用 `set`**：`set` 会覆盖已扣减的值。
3. **失效用版本号 `INCR`，不用 `KEYS`**：`KEYS` 阻塞整个 Redis。
4. **TTL 加随机抖动**：防缓存雪崩。
5. **`try` 要包住 `buildKey()`**：它内部也访问 Redis。
6. **反序列化用 `[].class`**：`readValue` 不会返回 `List`。

## Q12：这套系统还有什么问题？

主动说出来（面试官最欣赏这个）：

| 问题 | 影响 | 计划 |
|---|---|---|
| 内存队列 | 进程崩溃丢单 | 换 RocketMQ |
